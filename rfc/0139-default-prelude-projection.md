# RFC 0139: Default prelude projection

- Status: Implemented
- Depends on: RFC 0138

## Summary

After `core/prelude` executes, later module compilation projects its exported
function values into the implicit prelude. Generated bytecode therefore uses
the exact same closures for:

```forma
struct('None, fields)
```

and:

```forma
import prelude from "core/prelude";
prelude.struct('None, fields)
```

The projection occurs before bytecode compilation and after type analysis. The
kernel bootstrap remains available during tool-stage evaluation, where it is
required to compile the prelude module itself.

## Static interface audit

The analyzed `core/prelude` `ModuleInterface` is the public contract. Bootstrap
entries that require precise schemes must agree with the corresponding module
export. Engine construction fails if a shared name has a different scheme.

Model constructors currently have non-generic `Any`-shaped bootstrap typing at
tool stage; their authored module declarations improve explicit-import typing.
`validate` has a precise generic bootstrap scheme and must match its authored
export exactly.

This audit is the boundary fallback required by RFC 0136: the kernel may
bootstrap analysis, but it cannot silently publish a contract different from
the real prelude module.

## Installation order

`core/prelude` installs before `std` and Host native modules regardless of its
numeric native module ID. Its frozen export record is then reused by every
later module in the same `MainWorld`.

Resolver identity and native module ID remain independent of installation
order.

## Acceptance criteria

1. `core/prelude` installs before all other native modules.
2. Later built-in and user bytecode use its exported closures for implicit
   `struct`, `enum`, `union`, and `validate` bindings.
3. Explicit and implicit references compare as the same opaque function
   identity.
4. The generic `validate` scheme matches the module interface declaration.
5. A projection cannot omit or add a declared default-prelude export.
6. Strict execution and recoverable workspace construction install the same
   module set and interface.
7. Direct frontend analysis retains a deterministic kernel bootstrap when no
   module world exists.

## Implementation result

Native installation now orders `core/prelude` first, audits its exact export
set and `validate` body scheme, and retains its exported function values as the
default projection for every later built-in. User-module analysis replaces the
four bootstrap runtime entries with those same exported closures before
metadata and program bytecode are compiled.

The projection validates that runtime Dict fields and `ModuleInterface`
exports are identical. Tests exercise explicit typed model construction and
generic validation, then compare every explicit function with its implicit
counterpart using opaque function identity; all four comparisons are true.

Strict and recoverable worlds share the same native installer and resolver
registration. Standalone frontend analysis, which has no `MainWorld` or module
registry, intentionally retains the deterministic RFC 0137 bootstrap fallback.
